# 개발 원칙

## 필수 상태와 자원 사용

- 컬럼·프로세스·별도 자원은 실제 비즈니스 동작 또는 필수 일관성·복구 책임과 연결한다.
- 기존 데이터와 처리 경로로 충분하면 그 자원을 재사용한다.
- 기존 자원으로 계산 가능한 상태의 별도 저장은 DB 접근의 성능 문제가 근거로 확인된 경우에 검토한다.
- 등록 시각 등 합의한 공통 관례 외의 정보성·진단용 컬럼 추가에는 사용자 동의가 필요하다.
- 애그리거트의 일관성과 성능을 지키면서 상태와 절차의 중복을 최소화한다.
- 진단 상세는 로그·메트릭으로 보낸다. 업무 복구 상태의 저장 책임은 해당 모듈에 있다.

## 코드와 문서

- 사용하지 않는 코드·포트·설정·의존성·테스트·문서를 같은 작업에서 정리한다.
- 일회성 확인용 코드·스크립트·결과 덤프는 정리 대상이다.
- 반복 실행하는 회귀·통합·부하 시험은 현재 동작의 검증 책임과 실행 경로가 있어야 한다.
- 현행 문서와 주석은 현재 동작·계약·제약을 설명한다.
- 설계 선택이나 개발 실수에서 얻은 교훈은 [개발 사례](engineering/README.md)에 문제·판단·검증 근거와 함께 남긴다.
- 기획은 사용자 합의, 구현된 임시 정책, 미확정 항목을 구분한다. 코드에 있다는 사실만으로 기획 의도를 확정하지 않는다.
- 중요한 쿼리·프로세스·아키텍처 변경은 현재 의도와 실패 복구·영향 범위를 검토하고 방향을 공유한다.

## 데이터와 트랜잭션

- 초기 스키마는 신규 DB 기준의 Flyway V1부터 구성한다.
- 실제 DB·Docker volume 삭제는 별도 명시적 요청을 따른다.
- Conversation은 메시지·마감, Journal은 일기·수정본, Identity는 인증·권한을 소유한다.
- 모듈 사이의 업무 접근은 publicapi를 사용한다.
- LLM 호출은 DB 트랜잭션과 행 잠금 밖에서 실행한다.
- 사용자별 일관성은 해당 사용자의 짧은 잠금으로 보장한다.
- JPA 엔티티는 infrastructure에 두고 애그리거트 참조는 ID를 사용한다.
- 파생 쿼리를 우선하며 원자적 선점·upsert·카운터는 범위가 명확한 SQL로 구현한다.
- JOIN 회피와 함께 DB 왕복·읽는 행 수·JVM 집계 비용을 평가한다.

## 실행과 검증

- 역할별 실행 슬롯·DB 풀·공급자 예산을 관리하며 배포 인스턴스 합계를 계산한다.
- 재시도·복구·성공 판정의 소유자를 명확하게 둔다.
- 검증 범위는 목표 처리량·데이터 크기·실행 시간·자원 예산·합격 기준으로 한정한다.
- 변경한 업무 규칙을 가장 좁고 의미 있는 검사로 확인한다.
- 단위·실제 PostgreSQL 통합·fake 공급자 부하·실제 공급자 검증 결과를 각각 명시한다.
- 통과한 범위와 미검증 범위를 구분해 보고한다.
- Git 변경 작업은 사용자의 명시적 요청을 따른다.
