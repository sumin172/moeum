# 모음 — 개발 원칙

이 문서는 [목표 아키텍처](ARCHITECTURE.md)를 구현할 때 적용한다.
기존 구현과 호환시키기 위한 원칙이 아니라 신규 기준이다.

## 작업과 정리

- 리팩터링으로 사용하지 않게 된 코드·포트·설정·의존성·테스트·문서는 같은 작업에서 삭제한다.
- deprecated wrapper, 호환 alias, 호출자 없는 이벤트와 미래 기능의 빈 모듈을 남기지 않는다.
- 대체 기능이 아직 없는 현재 실행 코드를 무작정 삭제하지 않는다. 각 단계는 새 경로 연결과 옛 경로 제거까지 완료한다.
- Git의 commit/push/브랜치 변경/원격 issue·PR 변경은 명시적으로 요청받을 때만 수행한다.
- 문서는 과거 결정의 덧붙이기보다 현재 결정으로 다시 작성한다. 상태·가정·미확정 사항은 분리한다.
- 현재 코드에 있다는 이유만으로 새로운 설계에 유지하지 않는다.

## DB와 Flyway

- 아직 DB가 생성되지 않았다고 가정한다.
- 스키마 변경 단계에서는 최종 스키마를 만드는 Flyway 초기 파일을 V1부터 새로 구성한다.
- 과거 스키마 호환용 ALTER 연쇄, 데이터 backfill, 이중 쓰기, 구버전 API를 만들지 않는다.
- 신규 DB에서 Flyway 적용·JPA 매핑·제약조건을 검증한다.
- 이 정책은 설계와 저장소 파일에 대한 것이다. 실행 중인 DB나 Docker volume을 자동 삭제할 권한을 뜻하지 않는다.

## 책임과 트랜잭션

- Conversation은 원본과 하루 마감, Journal은 생성 결과와 사용자 수정본, Identity는 인증·권한을 소유한다.
- 다른 업무 모듈의 내부 구현과 테이블을 직접 사용하지 않는다. publicapi만 호출한다.
- 한 트랜잭션은 한 업무 모듈에서 끝난다. 모듈 사이 전달은 영속 등록 후 확인하며 중복에 안전해야 한다.
- LLM 호출 동안 DB 트랜잭션이나 행 잠금을 유지하지 않는다.
- 생성 입력은 최초 실행 직전에 원자적으로 확정한다. 이후 새 원본은 사용자 알림 없이 폐기하고 재시도에도 입력을 다시 열지 않는다.
- 저장 성공한 원본은 보존한다. 미접수 원본의 정책상 폐기를 저장 성공으로 응답하지 않는다.
- 사용자별 순서는 작고 짧은 잠금으로 보장하며 사용자 전체를 직렬화하지 않는다.
- 대화 한도는 요금제별 유한값이다. 클라이언트에 미리 공개하고 서버 접수 트랜잭션에서도 검증한다.
- 한도 초과 시 원본만 저장하는 경로를 만들지 않는다. 중복 전송과 실패 복구 재시도는 추가 차감하지 않는다.
- 일기 직접 수정은 JOURNAL_EDIT 구독 권한으로 보호한다. AI 재작성·문체·길이 설정은 제공하지 않는다.
- 재시도·리스·성공 판정의 소유자를 하나로 둔다. 공급자 클라이언트와 작업 실행기가 각각 재시도하지 않는다.

## 모델과 쿼리

- Aggregate는 일관성 경계다. 관계형 테이블 전체를 객체 그래프로 만들지 않는다.
- JPA @Entity는 infrastructure에만 둔다. 컬렉션 연관관계 대신 ID와 명시적 조회를 사용한다.
- 목록·마감 대상 조회에 본문을 읽지 않는다. 전역 원본 스캔과 사용자별 N회 조회를 피한다.
- JOIN 금지가 대량 JVM 집계나 과도한 round trip을 정당화하지 않는다.
- 파생 쿼리를 우선하되 원자적 선점·upsert는 작은 native SQL/JDBC로 격리한다.
- 사용자 소유 데이터는 userId를 직접 가지고, 사용자 요청 조회에도 userId 조건을 포함한다.
- append-only 데이터는 persist 또는 올바른 신규 판별로 저장한다.
- UUID는 식별자다. 다중 인스턴스의 커밋 순서나 원본 변경 번호로 대체하지 않는다.
- 컬럼은 저장량보다 소비처로 평가한다. 계산 비용을 줄이는 업무 상태는 저장하고, 진단 중복은 줄인다.

## 실행과 성능

- API·대화 응답·일기 생성은 독립적인 실행 역할과 자원 상한을 갖는다.
- 스케줄러는 실행 슬롯에 짧게 전달한다. 실제 워커 스레드가 시작한 뒤 선점하고 외부 호출을 수행한다.
- 실행 슬롯을 얻기 전에 다량의 작업을 선점해 리스를 소모하지 않는다.
- 인스턴스 증가 시 DB 풀 총합과 공급자 호출 총량도 증가한다. 인스턴스별 Semaphore만으로 전체 제한을 보장하지 않는다.
- 사용자 급증은 [부하 기준](CAPACITY.md)의 시나리오와 결과로 평가한다. 기간만으로 확장성을 보장하지 않는다.
- 가상 스레드는 공급자 처리 한도·DB 커넥션·메모리·호출 비용을 늘려주지 않는다.

## 관측과 보존

- 업무 복구 상태는 영속 저장한다. 진단 상세는 구조화 로그·메트릭으로 보낸다.
- request/trace ID, recordDayId, jobId, generationId, attempt, 오류 분류로 흐름을 연결한다.
- 원문·생성 본문·인증 토큰·인증 헤더를 예외 메시지나 외부 관측 시스템에 기록하지 않는다.
- 메트릭 label에 사용자 ID·작업 ID를 넣어 cardinality를 무한히 늘리지 않는다.
- 관측기 실패가 원본 저장 실패로 전파되지 않게 한다.
- 완료 작업의 보존 기간과 삭제 기준을 정한다. 활성/실패 복구 작업을 임의로 정리하지 않는다.
- 삭제 기능은 원본·파생 데이터·진행 중 작업·백업 보존을 함께 다룬다.

## 검증과 완료

- 변경한 업무 규칙의 시나리오를 테스트한다. 구현 내용을 그대로 복제하는 테스트는 만들지 않는다.
- DB 제약·선점·동시성은 실제 PostgreSQL 통합 테스트로 확인한다.
- 테스트 통과, 실제 공급자 스모크, 부하 검증을 구분해서 보고한다.
- 각 이슈는 새 경로 연결, 데드 코드 삭제, 문서 정리, 좁고 의미 있는 검증까지 끝나야 완료다.
