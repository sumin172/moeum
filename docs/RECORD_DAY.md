# 하루 기록과 자동 일기 정책

상태: 귀속·마감·전달·입력 동결과 R3 서버 한도·응답 순서·조회 계약을 구현했다. R4의 자동 보관·구독 수정·수정본 보호도 구현했으며 현재 계약은 [일기 계약](JOURNAL.md)을 따른다.
사용자가 설정한 마감 시각과 마지막 사용자 발화 장소의 타임존을 따른다는 요구는 확정이다.
아래 숫자·날짜 표시 기본안은 사용자 행동 데이터가 없는 설계 가정이며 구현 전 변경 가능하다.

## 용어

- RecordDay: 한 번 마감해서 일기로 만들 기록. UUID 식별자를 사용한다.
- displayDate: 화면에 보여주는 기록 날짜. 식별자나 전역 정렬 기준이 아니다.
- occurredAt: 클라이언트의 실제 발화 시각. 미래 허용 오차를 검증한다.
- acceptedAt: 서버가 입력을 받은 시각. 저장 요청 제한·비용 제한은 이 시각을 기준으로 한다.
- sourceRevision: 해당 기록의 사용자 원본이 추가될 때 증가하는 순번.
- closeAt: 현재 예약된 절대 마감 시각.
- closedAt: 확정된 논리적 마감 경계. 워커가 실제 실행한 늦은 시각과 구분한다.
- 생성 입력 확정: 최초 생성 실행 직전 Conversation이 원본을 잠그고 sourceRevision을 고정하는 순간. 이후 해당 기록의 새 원본은 받지 않는다.

## 기본 정책

1. 마감 이후 새 대화는 다음 RecordDay로 모은다. 마감이 23:00이면 23:00 정각부터 다음 기록이다.
2. 마감 설정 변경은 다음 기록부터 적용한다. 열린 기록은 자신의 마감 시각 설정 스냅샷을 유지한다.
3. 열린 기록의 타임존은 가장 최근 사용자 발화로 갱신한다. AI 응답, 앱 열기, 조회 요청은 갱신하지 않는다.
4. 닫힌 기록은 다시 열지 않는다. 생성 입력 확정 전에는 지연 원본을 포함할 수 있지만, 확정 이후에는 저장하지 않고 조용히 폐기한다.
5. 활동이 없으면 빈 RecordDay·생성 작업·일기를 만들지 않는다.
6. 생성 결과는 자동 보관한다. 확정 버튼은 없다.
7. 사용자 수정본은 자동 생성·재시도로 덮어쓰지 않는다.
8. 늦은 원본에 따른 일기 자동 갱신은 하지 않는다. 폐기는 화면 알림 없이 내부 결과로만 전달한다.

## 날짜 표시 기본안과 가정

마감 시각을 달력 날짜 구분과 무조건 동일시하지 않는다.
표시 날짜는 최초 기록 생성 시 결정하고 이후 타임존 이동에도 고정한다.
새벽 마감은 전날의 기록이라는 일반적인 기대를 반영하기 위해 다음을 기본안으로 둔다.

- 마감 시각이 00:00 이상 12:00 미만이면 마감 현지 날짜의 전날로 표시한다.
- 마감 시각이 12:00 이상이면 마감 현지 날짜로 표시한다.
- 12:00 구분은 제품 요구로 확정된 값이 아니라 명시적 가정이다.
- 예: 10/11 23:00 마감 → 10/11 기록. 10/12 02:00 마감 → 10/11 기록.
- 표시 날짜가 같아도 여행 중 서로 다른 기록이 생길 수 있다. DB unique(userId, displayDate)를 두지 않는다.
- API의 수정·조회 식별자는 recordDayId/journalId다. 날짜 조회는 목록 필터다.

정오 기준이 제품에 맞지 않으면 이 정책만 변경한다.
이를 이유로 기존 메시지의 귀속이나 식별자를 다시 계산하지 않는다.

## 마감 계산과 타임존 변경

새 기록은 적용 설정의 현지 마감 시각 중 첫 발화 이후 가장 가까운 시각을 closeAt으로 예약한다.
마감 현지 날짜와 시각 설정을 스냅샷으로 가지고, 타임존 변경 시 같은 현지 마감 약속을 새 zone으로 변환한다.
AI 응답이 뒤늦게 도착해도 마감 예약에는 관여하지 않는다.

마지막 장소는 사용자 발화의 occurredAt으로 비교한다.
동일 occurredAt이면 서버가 잠금 안에서 부여한 원본 순번으로 순서를 정한다.
생성 입력 확정 전에 접수한 과거 오프라인 메시지는 본문과 sourceRevision에 반영하되, 최신 장소를 과거로 되돌리지 않는다.
미래 발화 시각은 서버보다 최대 5분까지만 허용하는 것을 기본안으로 두며 잘못된 시각은 거부한다.

열린 기록의 장소 변경으로 새 closeAt이 이미 지난 시각이면 현재 트랜잭션 시각에 마감한다.
다음 날짜로 무조건 미루어 기록이 계속 늘어나는 정책을 사용하지 않는다.
새 예약이 첫 수집 경계부터 36시간을 넘기면 36시간 시점에 마감한다.
36시간은 날짜변경선 이동/잘못된 설정으로 무한히 열린 기록이 생기는 것을 막는 잠정 상한이다.
초과·즉시 마감 사유는 구조화 로그와 사용자에게 반환하는 마감 상태에 드러낸다.

DST로 존재하지 않는 시각은 gap 이후 최초 유효 시각, 두 번 존재하는 시각은 뒤의 offset을 선택한다.
offset 숫자를 영구 고정하지 않고 IANA zone 규칙으로 절대 시각을 계산한다.
DST gap/overlap과 날짜변경선 이동을 모두 테스트한다.

## 마감과 메시지 저장의 경합

같은 사용자의 기록 생성/귀속과 마감은 동일한 사용자 상태 → RecordDay 순서로 짧게 잠근다.
마감 작업은 사용자 간 잠금 대기로 전체 배치가 멈추지 않도록 건너뛰고 다음 회차에 처리할 수 있다.

- acceptedAt이 현재 closeAt 이전이고 메시지 저장이 먼저 잠금을 얻으면 원본 추가·장소 갱신 후 마감 여부를 다시 판단한다.
- acceptedAt이 closeAt 이후이면 워커가 아직 실행하지 않았어도 이미 마감 경계가 지난 것으로 취급한다.
- occurredAt이 닫힌 경계 이전인 지연 메시지는 생성 입력 확정 전이면 과거 기록에 추가하고, 확정 이후이면 폐기한다.
- occurredAt이 경계와 같거나 이후인 새 발화는 다음 기록에 속한다.
- 타임존 변경은 이미 닫힌 기록의 경계를 이동시키지 않는다.
- LLM 호출 동안 어떤 잠금도 유지하지 않는다.

현재 closeAt 도달 여부를 먼저 확인하므로, 마감 이후 장소 변경으로 과거 기록을 되살리지 않는다.
최초 생성 실행 직전 원본 추가와 같은 RecordDay 잠금 아래 sourceRevision을 한 번 고정한다.
입력 저장이 먼저 커밋되면 생성에 포함하고, 입력 확정이 먼저 커밋되면 새 원본을 폐기한다.
판정은 단순 HTTP 도착 시각 비교가 아니라 이 트랜잭션 순서로 결정한다.
고정한 입력은 실패 재시도·워커 재시작에서도 다시 열지 않는다.

## 오프라인·과거 기록

클라이언트는 알고 있는 recordDayId와 clientMessageId를 함께 보낼 수 있다.
서버는 소유권과 발화 시각의 기록 구간 적합성을 확인하고 임의의 과거 기록 주입을 허용하지 않는다.
recordDayId가 없으면 사용자별 보관된 절대 구간으로 먼저 귀속을 찾는다.
이미 저장한 메시지는 설정 변경으로 재귀속하지 않는다.

기록 자체가 없던 날의 오프라인 입력은 수신 시점의 설정과 메시지 zone으로 과거 구간을 계산해 닫힌 기록을 만든다.
이 경우 발화 당시 설정 이력이 없으므로 완전한 과거 재현이 아니라는 제한을 수용한다.
기존 구간과 겹치거나 둘 이상 후보가 있어 모호하면 임의 배정하지 않고 재선택 가능한 오류를 반환한다.
지연 원본의 폐기 여부를 메시지 나이로 제한하지 않는다. 해당 기록의 생성 입력이 확정됐는지가 기준이다.
미확정 기록의 지연 입력도 새 메시지 접수이므로 서버 요금제 한도 검증을 통과해야 한다.
기존 기록이 없는 과거 입력은 위 귀속 규칙에 따라 최초 생성 대상으로 등록할 수 있다.
이미 입력이 확정된 기록에 대한 지연 입력은 새 기록으로 우회 저장하지 않는다.

### 조용한 폐기와 재전송

- 먼저 소유권·입력 유효성과 clientMessageId 중복을 확인한다.
- 이미 저장된 메시지의 재전송이면 기존 저장 결과를 반환한다. 과거 저장 성공을 폐기로 바꾸지 않는다.
- 아직 저장되지 않은 원본이 입력 확정 이후 도착하면 저장·sourceRevision 증가·AI quota 소비·작업 등록 없이 종료한다.
- 응답은 내부 종결 결과 `DISCARDED_INPUT_FROZEN`으로 구분한다. 저장 성공으로 가장하지 않는다.
- 클라이언트는 이 결과를 받으면 별도 알림이나 날짜 재선택 요청 없이 전송 대기열에서 제거한다.
- 응답이 유실되어 재전송되어도 확정 상태는 유지되므로 같은 종결 결과를 반환한다.
- 폐기된 본문이나 메시지별 영구 폐기 이력을 DB에 쌓지 않는다. 필요하면 사유별 집계만 관측한다.
- 사용자가 일기를 실제로 열었는지는 판단 조건이 아니다. 생성 중·완료·실패 모두 입력 확정 상태를 유지한다.
- 일기 생성 실패 알림/재시도와 지연 원본의 조용한 폐기는 별개 정책이다.

과거 AI 응답을 새로 끼워 넣지는 않는다.

## 일기 생성·수정

| 상황 | 동작 |
|---|---|
| 최초 마감 | 기록 ID로 자동 생성 요청을 전달. 아직 원본 입력은 확정하지 않음 |
| 작업 대기 중 과거 원본 도착 | 생성 입력 확정 전이면 저장하고 최초 생성에 포함 |
| 최초 생성 실행 | Conversation에서 입력을 원자적으로 확정한 뒤 그 원본으로 생성 |
| 생성 중·완료 후 지연 원본 도착 | 조용히 폐기, 기존 일기·작업·입력 불변 |
| 자동 생성 실패 | 같은 확정 입력으로 재시도, 소진 시 사용자에게 생성 실패 상태 제공 |
| 생성 실패 이후 지연 원본 도착 | 입력은 다시 열지 않고 조용히 폐기 |
| 구독자 직접 수정 | 제목·본문과 편집 version 갱신 |
| 무료 사용자 수정 요청 | JOURNAL_EDIT 권한 부재로 거절, 현재 내용 불변 |
| 일기 직접 수정 경합 | version으로 충돌 감지, 먼저 저장한 내용 보존 |
| 작업 리스 회수 후 과거 작업 완료 | 작업 소유권·편집 version으로 과거 결과 저장 차단 |

늦은 원본에 따른 자동 갱신, 추가 원본 안내, 변경 합치기 타이머는 구현하지 않는다.
서버 실패 재시도는 같은 확정 입력으로 실행하며 대화 횟수를 추가 차감하지 않는다.
AI 재작성·문체·길이 설정은 제공하지 않는다.
원본 저장 성공으로 응답한 기록은 보존한다. 의도적으로 폐기한 미접수 원본과 저장 후 유실을 구분한다.

## 현재 서버 계약

- `POST /api/conversations/messages`: `clientMessageId/content/occurredAt/timezone`와 선택적 `recordDayId`를 받는다. 응답은 `status/recordDayId/message`다.
- 성공은 `ACCEPTED`와 메시지/AI 응답 상태를 반환한다. 동결 이후 새 입력은 `DISCARDED_INPUT_FROZEN`과 null message를 반환하며 본문·원본 버전·quota·응답 작업을 남기지 않는다. 클라이언트는 알림 없이 대기열에서 제거한다.
- 저장된 clientMessageId 재전송은 동결 여부와 관계없이 기존 성공을 반환한다. 소유권 또는 발화 구간 불일치는 404/409이며 미래 5분 초과 입력은 400이다.
- `GET /api/conversations/records?date=&limit=`은 기록 목록, `GET /api/conversations/records/{recordDayId}?after=&limit=`은 메시지·응답 상태·nextCursor를 반환한다. after는 정수 streamSequence이며 조회는 장소를 갱신하지 않는다.
- `GET/PUT /api/conversations/preferences`는 `closeTime`을 조회/저장한다. 새 설정은 다음 기록부터 사용하고 열린 기록의 스냅샷을 바꾸지 않는다.
- `GET /api/journals?date=`는 같은 표시 날짜의 여러 일기를 반환한다. 상세/수정/실패 재시도는 `/api/journals/{recordDayId}` 기준이다. 날짜 기반 기존 경로와 /today 별칭은 제공하지 않는다.

Conversation의 UserRecordState와 RecordDay는 메시지 컬렉션·JPA 관계를 보유하지 않는다. 저장·마감·동결은 사용자 상태 → 기록 잠금 순서로 직렬화한다. 발화/접수 시각은 PostgreSQL과 같은 마이크로초 정밀도로 맞춰 동시 발화는 sourceRevision 순서로 처리한다. 메시지는 recordDayId와 USER sourceSequence로 직접 조회한다.
마감 poll은 작은 열린 예약만 조회하고, 전달 poll은 닫힌 미확인 기록만 선점한다. 생성 요청은 Journal의 UNIQUE(user_id, record_day_id)로 한 번 등록한다. 확인 실패 후 재전달은 해당 제약만 충돌을 무시하고 다른 DB 오류는 전파한다.
첫 실행에서 Conversation 원본 버전을 동결하고 USER 메시지를 occurredAt/sourceSequence 순으로 읽는다. ASSISTANT는 늦게 완료될 수 있어 생성 입력에 포함하지 않는다. 재시도·리스 회수는 같은 frozenSourceRevision을 사용한다.
새 기록의 과거 발화는 7일 제한 없이 접수하지만 이미 닫힌 기록에는 새 AI 응답을 생성하지 않는다. 새 원본은 서버 UTC 기간의 현재 구독 한도를 통과해야 한다. 중복·폐기·실패 재시도는 추가 차감하지 않는다. 응답 순서·정수 커서·작업 묶음 상태·한도 조회의 상세 계약은 [대화 계약](CONVERSATION.md)을 따른다.
