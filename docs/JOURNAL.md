# 일기 생성·조회·수정 계약

생성 구간은 [하루 기록](RECORD_DAY.md), 기능의 전제는 [서비스 기획](PRODUCT.md)을 따른다.

## 생성 입력과 결과

생성 작업은 닫힌 기록 하나의 마지막 USER 스트림 순번까지 USER·ASSISTANT 문맥을 읽는다.
USER는 경험·감정의 사실 근거이고 ASSISTANT는 짧은 답변·부정·정정의 해석 문맥이다.
프롬프트 v3는 한국어 제목과 1인칭 본문을 JSON으로 요청한다.

JSON 파싱 뒤 제목·본문의 공백과 길이를 검사한다.
생성 결과 상한은 제목 200자·본문 20,000자(UTF-16 길이)다.
실패 시 생성 원문을 예외에 넣지 않고 잘못된 출력으로 처리한다.

일기는 recordDayId당 현재 결과 하나이며 생성 즉시 조회할 수 있다.
본문은 TEXT로 저장한다. 결과는 제목·본문·표시 날짜와 수정 version을 가진다.
사용자 수정은 현재 내용이 실제로 달라질 때 version을 증가시킨다.

## 최대 입력의 검증 범위

현재 구독 한도는 UTC 하루 100회, 메시지 최대 길이는 4,000자다.
기록 경계는 장소 타임존과 설정 마감으로 정해지며, 여행 중 하나의 기록이 여러 UTC 사용 기간에 걸칠 수 있다.
입력 조립 시험은 USER 300개·1,200,000자에 합성 AI 300개·각 1,000자를 더해 약 150만 자의 전달을 검사한다.
AI 길이는 합성 가정이며 실제 출력은 공급자 토큰 설정에 달려 있다.
300개는 입력 조립 시험의 크기이며 기록당 최대 접수량을 뜻하지 않는다.

현재 생성기는 해당 기록의 입력 전체를 한 호출로 전달한다.
실제 모델 토큰 한도에는 역할·시각·시스템 프롬프트와 출력 여유도 포함된다.
단위 시험의 입력 전달 확인과 실제 공급자의 처리 가능성·품질·동시 메모리 검증은 별개다.
최대 정상 입력의 실제 모델 처리 가능성은 미검증이다.

## 저장과 수정 충돌

LLM 호출은 트랜잭션 밖에서 수행한다.
저장 트랜잭션은 작업 행의 PROCESSING과 version을 확인한 후 일기 INSERT와 작업 완료를 함께 커밋한다.
만료된 워커의 늦은 결과는 소유권 검사에서 거절한다.
기록 유일키가 충돌하면 기존 일기를 그대로 사용한다.

사용자 수정은 JOURNAL_EDIT 권한과 클라이언트 version을 검사하고 JPA @Version으로 동시 충돌을 검출한다.
자동 저장은 기존 결과를 갱신하지 않으므로 현재 사용자 수정본을 보호한다.
직접 수정의 현재 내용 검증은 제목·본문 공백 검사이며 생성 출력 길이 검사와 별도다.

## API

| API                                                  | 응답·동작                             |
|------------------------------------------------------|---------------------------------------|
| GET /api/journals?date=                              | 표시 날짜별 생성 일기 목록, 본문 포함 |
| GET /api/journals/{recordDayId}                      | recordDayId, journal, generation      |
| PUT /api/journals/{recordDayId}                      | title/body/version으로 수정           |
| POST /api/journals/{recordDayId}/generation-attempts | 실패한 같은 작업 복구                 |

일기 응답은 recordDayId, displayDate, title, body, version, editable을 포함한다.
표시 날짜가 같은 기록이 여러 개면 각각 반환한다.
상세 조회는 현재 일기와 생성 작업을 조회하며 작업 정리 후 generation은 null일 수 있다.
생성 전 journal은 null이다.

수정 권한은 요청 시 현재 유효 구독으로 판단한다.
권한 부재는 403, 공백 입력은 400, 없는 일기는 404, 낡은 version과 동시 충돌은 409다.
성공 응답의 version을 다음 수정 요청에 사용한다.

## 생성 실패 복구

무료·구독 모두 실패한 같은 작업을 재시도할 수 있으며 대화 횟수를 추가 차감하지 않는다.
PENDING/PROCESSING의 반복 요청은 현재 작업을 반환한다.
완료 결과가 있거나 COMPLETED 작업이면 409, 작업이 없으면 404다.

| 정책             | 현재 기본값                                              |
|------------------|----------------------------------------------------------|
| 자동 시도 상한   | 첫 시도 포함 5회                                         |
| 자동 대기        | 1분, 5분, 30분, 2시간 + jitter                           |
| 누적 시도 상한   | 자동·수동·리스 회수 합계 7회                             |
| 수동 재시도 대기 | 실패 시각부터 1분                                        |
| 429 최소 대기    | 5분과 공급자 Retry-After, 일반 backoff 중 가장 늦은 시각 |
| 생성 리스        | 5분                                                      |

일시적 오류는 제한된 재예약, 인증·명확한 입력 오류는 자동 반복 중단으로 처리한다.
잘못된 출력은 전체 시도 횟수 기준 두 번째 시도부터 자동 재예약하지 않는다.
수동 대기 중 요청은 429, 누적 상한 소진은 409다. 시도 횟수는 누적된다.

## 보관과 검증

원본 대화와 현재 일기는 보관한다. 완료·최종 실패 작업은 30일 뒤 [보존 정책](OBSERVABILITY_RETENTION.md)으로 정리한다.
