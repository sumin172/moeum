# 마감 경계로 생성 입력을 고정하기

## 서비스의 요구와 초기 오해

서비스는 AI와 나눈 일상 대화로 정해진 시간에 일기를 만드는 경험이다.
대화 횟수는 상한이며 일기를 만들기 위해 채워야 할 목표가 아니다.
마감 후 처음 들어온 대화는 다음 기록에 속한다.

초기 설계에는 클라이언트 발화 시각으로 과거 기록을 찾거나 복원하고,
생성 입력 동결 여부에 따라 늦은 원본을 접수·폐기하는 경로가 있었다.
이 구조는 입력을 안정적으로 고정하려는 목적이 있었지만,
워커 실행 시점에 따라 같은 새 메시지의 처리 결과가 달라질 수 있었다.

## 선택과 단순화

사용자는 마감 이후의 새 대화를 다음 기록으로 취급한다는 정책을 명확히 했다.
이에 따라 귀속 기준은 사용자 상태 잠금 후 서버 접수 시각으로 정리됐다.
이미 저장한 메시지는 clientMessageId로 재사용하고, 새 메시지는 현재 열린 기록에 저장한다.

닫힌 기록에는 새 USER가 들어오지 않는다.
따라서 별도 FreezeRecord나 frozen_source_revision 같은 상태 없이
RecordDay의 마감과 마지막 USER 메시지의 기존 스트림 순번으로 입력을 결정할 수 있다.
과거 귀속·복원·동결 후 폐기 경로도 이 정책에서 필요성을 잃었다.

## 문맥 품질

USER만 입력하면 AI가 “팀장님에게 칭찬받았어?”라고 묻고 사용자가 “응, 처음이야”라고 답한 의미를 잃는다.
일기 입력에는 마지막 USER까지의 ASSISTANT 문맥을 포함하고,
USER를 사실 근거, ASSISTANT를 해석 자료로 구분했다.
마지막 USER 뒤의 응답과 마감 이후의 응답은 생성 입력에서 제외한다.
본문은 사용자 상태 잠금 밖에서 읽는다.

## 보관 정책과의 관계

과거 대화를 화면에 얼마 동안 보여줄지는 원본 보관 기간과 다른 선택이다.
사용자는 UI 방향이 미정이므로 데이터를 보관하는 방향을 선택했다.
장기 보관 자체가 과거 일기의 입력을 다시 열거나 생성 작업을 계속 보존할 이유가 되지는 않는다.

## 검증과 한계

ClosedJournalInputIntegrationTest와 DayBoundaryIntegrationTest는 마감 이후 접수·중복 재전송·늦은 AI 응답·재시도의 입력 경계를 검사한다.
LlmJournalGeneratorTest는 역할과 짧은 긍정·부정·정정 문맥의 전달을 검사한다.
실제 모델이 모든 문맥을 올바르게 해석한다는 품질 보장은 별도 평가다.

교훈은 새 고정 상태를 만들기 전에 제품 정책이 이미 불변으로 만드는 범위를 찾는 것이다.
현재 계약은 [하루 기록](../RECORD_DAY.md)에 있다.
