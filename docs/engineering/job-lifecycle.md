# 실패 격리와 작업 수명을 함께 설계하기

## 전달 트랜잭션의 선택

마감과 최초 생성 예약을 같은 DB 트랜잭션으로 합치면 전달 리스·확인 처리를 줄일 수 있다.
하지만 기존 전달 분리에는 Journal 등록 실패를 대화 접수에서 격리하려는 의도가 있었다.
복구 가능한 구조라는 사실만으로 복잡성을 정당화할 수는 없지만,
현재 보장과 실패 범위를 이해하지 않은 채 통합을 필수 수정으로 권장하는 것도 부정확했다.

현재 선택은 Conversation 마감·전달 선점, Journal 등록, Conversation 확인의 독립 트랜잭션이다.
등록 전 종료는 전달 리스로 회수하고, 등록 후 종료는 기록 유일키로 중복을 막는다.
실제 JVM 강제 종료 시험에서 두 지점의 복구를 확인했다.

## 오류와 재시도

오류 종류와 관계없이 같은 횟수로 반복하고 수동 요청마다 횟수를 초기화하면
설정 오류도 반복 호출하고 실패 사이클을 무한히 갱신할 수 있다.
일시적 장애·호출 제한·영구 오류·잘못된 출력으로 구분하고
기존 시도 횟수와 예약 시각으로 자동 반복, 수동 대기, 누적 상한을 집행하도록 정리했다.

선행 답변을 최종 실패 처리한 뒤 후속 답변이 진행됐다면,
설정을 고쳤다는 이유만으로 과거 답변을 다시 끼워 넣을 수는 없다.
수동 복구 허용 여부는 오류 종류뿐 아니라 대화 순서와 함께 판단한다.

## 완료 이력과 업무 사실

과거 실패의 재시도 가능 여부를 후속 완료 작업에서 확인하면,
실패 하나 때문에 같은 기록의 완료 작업 전체가 계속 남을 수 있다.
이미 저장된 ASSISTANT의 source_sequence로 후속 완료를 확인하고,
PROCESSING 작업으로 후속 실행을 확인하면 완료 작업 보존과 재시도 판단을 분리할 수 있다.
접수만 된 PENDING은 이미 진행한 응답으로 취급하지 않는다.

실패 작업 자체의 만료 정책은 완료 이력 정리와 별개다.
현재 실패·활성 작업을 임의로 지우지 않는 계약을 유지한다.

## 검증

ResponseRetryIntegrationTest와 TerminalJobRetentionIntegrationTest는
후속 진행에 따른 재시도 거절, 완료 이력 정리 후 동일 판단, 중복 접수 무차감을 검사한다.
JobStateTest는 오류 분류별 재예약과 수동 재시도 제한을 검사한다.
현재 계약은 [대화](../CONVERSATION.md), [일기](../JOURNAL.md), [보존](../OBSERVABILITY_RETENTION.md)에 있다.
