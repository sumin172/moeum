# 성능 시험이 실제로 증명한 범위

## 목표와 관측값

250 RPS라는 목표와 실제 접수·완료 수는 별개다.
주입기가 버린 요청을 제외한 응답만 빠르다고 목표 처리량을 통과한 것은 아니다.
시험은 예정·전송·접수·완료·주입기 드롭을 함께 기록한다.

현재 구조의 2026-10-20 60초 시험은 각 구간 15,000건을 모두 접수·완료했다.
3분 시험은 실행별 변동이 있었고 일부 실행에서 API DB 풀 대기와 주입 드롭이 발생했다.
마지막 3분 실행에서는 각 구간 45,000건을 완료했지만
혼합 API p95 증가율이 20.24%로 목표 20%를 근소하게 넘었다.
현재 검증 범위는 [검증 현황](../CAPACITY_RESULTS.md)에 있다.

## 시험 입력도 원인을 만든다

최초 주입기는 구간마다 ceil(예정 요청/18)명의 새 사용자를 만들어 순환했다.
길이를 60초에서 3분으로 늘리면 초반 약 10초의 신규 기록 생성량도 늘었다.
그래서 지속 부하는 첫 메시지·응답을 준비한 사용자 집단으로 분리했다.
그래도 일부 실행에서 정체가 재현되어 신규 기록 집중만을 원인으로 확정하지 않았다.

혼합 구간은 일기 1,000건을 지정했지만 이전 구간의 기록도 실제 마감되어
마지막 3분 실행의 일기 워커 호출은 약 2,141건이었다.
지정 fixture 수와 실제 총부하를 함께 봐야 한다.

checkpoint 쓰기 시간도 측정했지만 지연이 낮은 구간에서도 긴 쓰기가 관측됐다.
이 상관관계만으로 쿼리·스키마를 바꾸는 근거로 삼지 않았다.

## 시간과 검증 책임

일기 완료가 부하 주입 구간 뒤에 일어날 수 있다.
수정 권한·버전 충돌·다음 기록 귀속 검사는 생성 완료 후에도 수행하도록 했다.
짧은 도구 검증에서는 이 경로를 확인하지만 장시간 성능 합격을 대신하지 않는다.

429 시험은 실제 리스 복구와 별도로 재시도 최소 대기를 2초로 설정한다.
운영 최소 대기값과 시험의 drain 제한을 혼동하면 정상 복구도 시간 초과로 오판할 수 있다.

## 해석의 한계

fake 공급자는 시스템의 저장·실행·복구를 시험한다.
실제 공급자의 토큰 한도·비용·해석 품질·RPM/TPM은 별도 검증이다.
매초 수동 정리 호출 결과는 운영 10초 스케줄의 장시간 유입·삭제 균형을 입증하지 않는다.
50,000개 과거 기록은 6개월 운영 누적량 전체의 검증이 아니다.

시험은 범위를 닫고 통과·실패·미검증을 보고한다.
측정 근거 없는 자원 추가나 합격을 위한 기준 완화는 성능 개선의 증거가 되지 않는다.
