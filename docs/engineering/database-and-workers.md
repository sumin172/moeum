# DB 왕복과 커넥션 점유가 만든 병목

## 중복 조회와 건별 선점

초기 부하 시험에서 메시지 저장의 반복 상태 조회와 신규 엔티티 merge의 선행 SELECT,
작업별 선점 왕복이 처리 지연에 기여했다.
기존 기록 저장의 중복 접근을 줄이고 append 데이터는 persist로 저장했다.
대화 워커는 남은 실행 슬롯을 예약한 뒤 작은 배치로 선점하도록 구성했다.

2026-10-18 로컬 시험은 PostgreSQL 4 CPU·4GiB, 기록 50,000개·메시지 약 200만 개,
250 RPS·60초, fake 대화 1초, API 풀 16 조건이었다.

| 단일 대화 워커 조건 | 접수/예정 | API p95 | 작업 대기 p95 |
|---|---:|---:|---:|
| 중복 조회 정리 전·건별 선점 | 13,288/15,000 | 3,528.8ms | 51,015.9ms |
| 중복 조회 정리 후·건별 선점 | 15,000/15,000 | 234.0ms | 17,087.4ms |
| 중복 조회 정리 후·배치 선점 | 15,000/15,000 | 317.6ms | 1,424.5ms |

순차 로컬 실험이며 반복 실험의 인과 효과나 신뢰구간을 구한 결과는 아니다.
저장 API와 워커 대기 병목을 따로 보아야 한다는 근거로 사용했다.

배치 선점은 실행 가능한 슬롯 이내에서만 수행한다.
기록 잠금 뒤 새로운 READ COMMITTED 문장에서 선두 작업을 다시 확인하여
동시에 재시작된 과거 작업을 후속 작업이 추월하지 않게 한다.

## 입력 조회의 커넥션 중첩

일기 입력 조회의 NOT_SUPPORTED 범위에서 JDBC 연결을 붙든 채 JPA 연결을 추가로 요구하는 문제가 있었다.
일기 슬롯과 풀을 각각 8로 둔 250건 시험에서 4건만 완료되고 연결 대기가 쌓였다.
해당 트랜잭션 범위를 제거한 뒤 같은 250건이 완료됐다.

“트랜잭션 밖”이라는 표기만으로 실제 연결 점유를 단정할 수 없었다.
JDBC와 JPA를 함께 사용하는 경로에서는 자원 바인딩과 실제 풀 사용을 확인해야 한다.
JournalInputConnectionIntegrationTest는 풀 연결 하나로 입력을 읽는 계약을 지속 검사한다.

## 처리량과 자원 예산

고정 간격마다 한 배치만 처리하면 대상이 남아 있어도 처리량에 낮은 상한이 생긴다.
마감·전달·정리는 작은 배치를 유지하면서 실행당 반복 횟수와 시간 예산을 적용한다.
측정 결과에 따라 간격·동시성을 조정하되 DB 부하와 공급자 예산을 함께 본다.

현재 실행 구성은 [실행 역할](../WORKER_ROLES.md)에 있다.
