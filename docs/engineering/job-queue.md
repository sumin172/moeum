# DB 작업 큐와 대안 비교

대화 응답·일기 생성은 PostgreSQL 작업 테이블과 역할별 워커로 실행한다.
이 문서는 메시지 브로커와 DB 기반 작업 라이브러리를 현재 구현과 비교한다. 현재 동작은 [아키텍처](../ARCHITECTURE.md)와 [실행 역할](../WORKER_ROLES.md)을 따른다.

## 메시지 브로커

사용자 메시지 저장과 응답 작업 등록은 함께 성공하거나 함께 실패해야 한다.
Kafka·RabbitMQ로 작업을 전달하면 DB 커밋과 발행이 분리되어 Transactional Outbox가 필요하다.
Outbox는 DB 테이블과 발행 폴러이므로, 그 테이블을 작업 큐로 직접 선점하면 브로커와 발행기 운영이 빠진다.

현재 목표 규모는 하루 대화 약 400회·일기 약 40회이고, 작업 하나는 수백 ms~수 초의 LLM 호출이다.
1초 poll 지연과 DB 큐 처리량은 이 규모의 제약이 아니라고 판단했다.

## DB 기반 작업 라이브러리

db-scheduler를 소스(커밋 466ff4b, 2026-10-12)로 확인했다.
JobRunr·Quartz는 소스로 확인하지 않았다. Quartz는 트리거 관리 중심이며, 사용자별 마감은 close_at 인덱스 조회로 충분하다.

| 항목            | db-scheduler                                                             | moeum                                                       |
|-----------------|--------------------------------------------------------------------------|-------------------------------------------------------------|
| 기본 선점       | 후보 조회 후 version 조건 UPDATE(낙관적)                                 | SKIP LOCKED 단일 UPDATE                                     |
| PostgreSQL 선점 | 선택 시 SKIP LOCKED 단일 문장. moeum과 같은 구조                         | 위와 같음                                                   |
| 장애 감지       | 실행 중 heartbeat 5분 갱신, 6회 누락(30분) 후 재예약                     | 고정 lease 만료(대화 2분·일기 5분) 후 재선점                |
| 펜싱 범위       | 라이브러리 행의 완료·재예약만 version 검사                               | 업무 결과 저장과 작업 완료를 같은 트랜잭션에서 version 검사 |
| 완료 작업       | 일회성 작업은 행 삭제                                                    | 상태 보존·API 노출 후 보존 기간 뒤 정리                     |
| 순서            | priority만 제공                                                          | 기록별 선두 작업만 선점                                     |
| 등록 트랜잭션   | Spring 스타터가 DataSource를 TransactionAwareDataSourceProxy로 감싸 참여 | 메시지와 같은 트랜잭션                                      |

낙관적 선점을 기본으로 둔 것은 SKIP LOCKED가 없는 DB까지 지원하기 위해서다.
moeum은 PostgreSQL 전용이므로 처음부터 SKIP LOCKED를 사용한다.

heartbeat는 프로세스가 살아 있는 동안 긴 작업을 빼앗기지 않는다. 대신 살아 있는 프로세스의 멈춘 작업은 회수하지 못하고 기본 감지 시간이 길다.
lease는 작업이 멈춰도 정해진 시간 뒤 회수한다. 정상이지만 느린 작업도 회수될 수 있어 외부 호출 timeout보다 길게 잡는다.
작업이 LLM 호출 한 번이고 사용자가 답을 기다리므로 lease를 유지한다.

라이브러리는 핸들러 실행 뒤 별도 갱신으로 완료를 기록한다. 리스를 잃은 실행의 늦은 업무 쓰기는 막지 않으므로 업무 쓰기를 멱등으로 만들어야 한다.
교체로 줄어드는 코드는 platform/job과 WorkerPool의 범용 실행부다.
기록별 순서, 마감·전달 리스, 오류별 재시도 정책, 사용자에게 보이는 작업 상태는 그대로 남고 작업 상태가 두 테이블로 나뉜다.

## 재검토 조건

- 작업 대기 p95가 목표를 넘고 슬롯·워커 증설로 해소되지 않는다.
- 작업 행 갱신이 DB 쓰기·vacuum 병목으로 관측된다.
- 같은 이벤트를 여러 독립 소비자가 받아야 한다.
- 작업 조회·재처리 대시보드 같은 운영 기능이 필요하다.

라이브러리를 다시 검토할 때는 업무 결과의 펜싱, 메시지와 작업의 원자적 등록, 기록별 순서를 확인한다.

## 검증

JobClaimIntegrationTest는 동시 선점 중복 방지와 lease 회수 뒤 늦은 저장 거절을 검사한다.
ConversationOrderingIntegrationTest는 기록별 선두 선점과 다중 워커의 기록 간 병렬 진행을 검사한다.
fake 공급자 시험의 처리량과 장애 복구 범위는 [검증 현황](../CAPACITY_RESULTS.md)을 따른다.
