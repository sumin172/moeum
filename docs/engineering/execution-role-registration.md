# 실행 역할별 빈 등록 방식

같은 backend jar를 API·대화 워커·일기 워커로 실행한다. 현재 실행 구성은 [실행 역할](../WORKER_ROLES.md)을 따른다.
이 문서는 역할별 빈 등록 방식의 대안과 현재 방식을 유지하는 근거를 설명한다.

## 문제

Gradle 모듈은 도메인(identity·conversation·journal) 기준이고 실행 역할은 배포 기준이다. 두 축은 교차한다.
한 모듈 안에 API 진입점과 워커 진입점이 함께 있고, JWT·Google·LLM 공급자 같은 외부 의존성은 해당 역할에서만 설정을 갖는다.
컴포넌트 스캔은 발견한 빈을 모두 등록하므로 역할 구분에는 별도 장치가 필요하다.

## 현재 방식

빈마다 Spring 스테레오타입과 `@ConditionalOnRole`로 등록 역할을 지정한다. `moeum.runtime.roles`와 지정 역할이 하나라도 겹치면 등록한다.
지정 대상은 진입점(컨트롤러·예외 advice·스케줄러·보안 필터), 역할 전용 의존성(LLM·JWT·Google·refresh token), 역할 전용 Properties, 워커 설정이다.
application service·repository·공통 Properties는 지정하지 않고 모든 역할이 공유한다.

등록 여부와 역할은 클래스 파일에서 보인다. 역할별 목록은 한곳에 모이지 않으며 `@ConditionalOnRole` 사용처로 확인한다.
지정하지 않은 빈은 모든 역할에 등록되므로 지정 누락은 기동 실패 없이 잘못된 등록으로 이어질 수 있다. 실행 경로를 바꾸는 누락은 보호 장치가 검사한다.

## 대안

| 대안                                  | 판단 | 근거                                                                      |
|---------------------------------------|------|---------------------------------------------------------------------------|
| 모듈 소유 역할 설정(`@Import`)        | 기각 | 원본 클래스에서 빈 여부가 사라지고, 누락 방지 효과는 검사 규칙이 대신한다 |
| 역할 스테레오타입 어노테이션          | 기각 | 어노테이션 한 줄을 줄이는 대신 Spring 스테레오타입의 레이어 의미를 가린다 |
| 패키지 기반 조건부 스캔               | 기각 | 도메인 패키지가 역할에 종속되고 스캔 경로가 겹친다                        |
| 등록 후처리기로 정의 제거             | 기각 | Configuration 처리 순서와 의존 관계에 의존한다                            |
| 역할별 Gradle 모듈·앱                 | 기각 | 도메인 코드 공유가 커서 모듈만 늘고, 서비스 분리 축과도 다르다            |

### 모듈 소유 역할 설정

각 모듈이 `ConversationWorkerConfiguration` 같은 역할 설정을 소유하고 역할 전용 클래스를 `@Import`한다. 조건은 설정 클래스에만 둔다.
클래스 단위로 지정하므로 도메인 패키지를 유지하고, 역할별 빈 목록이 설정 클래스에 드러난다.

워커 전용 빈에 적용해 확인한 제약은 다음과 같다.

- import 대상은 스테레오타입을 갖지 않으므로 원본 클래스에서 빈 여부와 역할이 보이지 않는다. 목록과 클래스를 함께 봐야 등록을 알 수 있다.
- `@Component`·`@Configuration` 같은 스테레오타입이 남은 import 대상은 역할 설정이 꺼져도 메인 스캔으로 등록된다. import와 스캔이 겹치면 정의가 하나로 합쳐져 격리가 조용히 깨진다.
- 역할 전용 클래스를 평소처럼 `@Component`로 작성하면 스캔으로 모든 역할에 등록된다. 의도를 선언하지 않은 누락은 빈 단위 지정과 같이 막지 못한다.
- 다른 빈이 참조하지 않는 스케줄러는 import를 빠뜨려도 기동은 성공하고 실행만 빠진다.
- 컨트롤러는 MVC 핸들러 인식에 `@RestController`가 필요하므로 메인 스캔에서 `@Controller`·`@ControllerAdvice`를 제외해야 한다.
- import한 일반 클래스에도 `@Scheduled`와 `@Transactional` 후처리가 적용된다. 스테레오타입을 떼면 kotlin-spring이 클래스를 열지 않으므로 메서드에만 `@Transactional`을 둔 클래스는 직접 열어야 한다.

중앙 목록의 이득은 가독성이고, 지정 누락의 방지는 등록 방식보다 검사 규칙에서 나온다.

### 역할 스테레오타입 어노테이션

`@Component`와 `@ConditionalOnRole`을 합성한 `@ConversationWorker` 같은 어노테이션이다. 한 줄로 빈 여부와 역할을 표현하고 사용처 검색이 역할별 목록이 된다.
`@Service`·`@Component`의 레이어 표시를 대체하고, 프로젝트 고유 어노테이션을 알아야 등록을 읽을 수 있다.
누락 검사는 `@ConditionalOnRole`을 직접 읽는 방식으로도 같게 구현된다.

### 패키지 기반 조건부 스캔

세 모듈의 `application.command`는 공통 서비스와 워커 전용 실행기가 섞여 있다. 역할에 맞추려면 도메인 패키지를 재배치해야 한다.
`@ConfigurationPropertiesScan`은 컴포넌트 스캔과 별도 경로로 Properties를 등록하므로 패키지 스캔만으로 역할 전용 Properties를 격리하지 못한다.
메인 애플리케이션의 `com.moeum` 전체 스캔과 역할별 스캔도 겹친다.

## 판단

역할은 셋으로 안정적이고 단기 확장은 API 추가다. 빈 하나의 등록 비용은 어노테이션 한 줄이며 빈 수에 비례해 늘 뿐이다.
등록 방식의 전환은 구성 가독성을 얻는 대신 클래스 파일의 가독성이나 Spring 관례를 내준다.
빈 단위 지정을 유지하고, 지정 누락은 등록 방식이 아니라 검사로 막는다. 검사가 보장하는 범위와 허용한 한계는 아래 보호 장치에서 정한다.
등록 방식의 전환은 도메인 로직과 별도로 할 수 있지만 빈 이름·스캔 중복·kotlin-spring 프록시와 역할별 기동을 다시 검증해야 한다. 재검토 조건이 생길 때 판단한다.

클래스의 등록 선언과 역할별 중앙 목록을 모두 직접 관리하면 두 곳을 동기화해야 하고, 어긋남을 다시 검사해야 한다.
등록의 원본은 클래스 선언 한곳에 두고, 역할별 목록은 `@ConditionalOnRole` 사용처 검색과 역할별 기동 테스트로 얻는다.

서비스 분리의 축은 실행 역할이 아니라 도메인이다. 분리 비용의 중심은 모듈 간 호출·데이터 소유권·트랜잭션 경계다.
빈 단위 지정은 클래스와 함께 이동하므로 분리를 막는 결합이 아니다. 공유 enum인 `ExecutionRole`은 분리할 때 서비스별로 정의한다.

## 보호 장치

검사 계약과 범위는 [역할 등록 검사](../WORKER_ROLES.md#역할-등록-검사)를 따른다. 이 절은 검사 범위를 정한 근거를 설명한다.

역할 전용 빈의 지정을 빠뜨리면 빈의 성격에 따라 결과와 검출 시점이 다르다.

| 지정을 빠뜨린 빈                               | 다른 역할에서의 결과                | 검출                       |
|------------------------------------------------|-------------------------------------|----------------------------|
| 스스로 실행되는 빈                             | 해당 역할이 아닌 곳에서도 실행된다  | ExecutionRoleRulesTest     |
| 역할 전용 빈에 의존하는 빈                     | 의존 대상이 없어 기동이 실패한다    | 역할별 기동 테스트         |
| 스스로 실행되지 않고 공통 빈에만 의존하는 빈   | 생성되지만 호출되지 않는다          | 검사하지 않는다            |

마지막 경우는 실행 경로가 바뀌지 않으므로 허용한다.

의존 관계는 정적 검사를 두지 않는다. 생성자 선택·qualifier·빈 이름 같은 Spring의 빈 해석을 테스트에서 재구현해야 하고, 해석하지 못한 경우를 통과시키지 않으려면 검사기 자체의 검증도 필요하다.
역할별 기동 테스트가 같은 누락을 원인 클래스와 함께 보고하므로 정적 검사가 더하는 것은 이른 피드백뿐이다.

실행 동작 검사는 정해 둔 어노테이션·타입과 이름이 `Listener`로 끝나는 어노테이션에 한정된다. 그 밖의 진입 장치는 규칙에 추가하기 전까지 검사되지 않는다.
유지 비용은 둘로 나뉜다. ArchUnit 규칙은 새 실행 역할이나 새 진입 장치에서만 바뀌고, 기동 테스트의 필수 빈 목록은 역할 전용 빈을 추가할 때 갱신한다.

## 재검토 조건

- 새 실행 역할이 늘어 역할 조합이 복잡해지거나, 같은 클래스를 역할마다 다르게 연결해야 한다.
- 새 진입점 종류(메시지 소비자·아웃박스 발행기 등)가 추가된다.
- 도메인 모듈을 별도 프로세스로 분리한다.
- 역할 지정 누락이나 잘못된 등록이 테스트를 통과해 실제 문제로 이어진다.
