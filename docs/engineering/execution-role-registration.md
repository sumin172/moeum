# 실행 역할별 빈 등록 방식

같은 backend jar를 API·대화 워커·일기 워커로 실행한다. 현재 실행 구성은 [실행 역할](../WORKER_ROLES.md)을 따른다.
이 문서는 역할별 빈 등록 방식의 대안과 현재 방식을 유지하는 근거를 설명한다.

## 문제

Gradle 모듈은 도메인(identity·conversation·journal) 기준이고 실행 역할은 배포 기준이다. 두 축은 교차한다.
한 모듈 안에 API 진입점과 워커 진입점이 함께 있고, JWT·Google·LLM 공급자 같은 외부 의존성은 해당 역할에서만 설정을 갖는다.
컴포넌트 스캔은 발견한 빈을 모두 등록하므로 역할 구분에는 별도 장치가 필요하다.

## 현재 방식

빈마다 `@ConditionalOnRole`로 등록 역할을 지정한다. `moeum.runtime.roles`와 지정 역할이 하나라도 겹치면 등록한다.
지정 대상은 진입점(컨트롤러·예외 advice·스케줄러·보안 필터), 역할 전용 의존성(LLM·JWT·Google·refresh token), 역할 전용 Properties, 워커 설정이다.
application service·repository·공통 Properties는 지정하지 않고 모든 역할이 공유한다.

이 방식은 역할별 구성이 클래스마다 흩어져 한곳에서 보이지 않는다.
지정하지 않은 빈은 모든 역할에 등록되므로 지정 누락이 기동 실패 없이 잘못된 등록으로 이어질 수 있다.

## 대안

| 대안                           | 판단 | 근거                                                           |
|--------------------------------|------|----------------------------------------------------------------|
| 패키지 기반 조건부 스캔        | 기각 | 도메인 패키지가 역할에 종속되고 스캔 경로가 겹친다             |
| 모듈 소유 역할 설정(`@Import`) | 보류 | 구성은 명시적이지만 등록 경로가 늘고 기동 경로 전체를 바꾼다   |
| 등록 후처리기로 정의 제거      | 기각 | Configuration 처리 순서와 의존 관계에 의존한다                 |
| 역할별 Gradle 모듈·앱          | 기각 | 도메인 코드 공유가 커서 모듈만 늘고, 서비스 분리 축과도 다르다 |

### 패키지 기반 조건부 스캔

세 모듈의 `application.command`는 공통 서비스와 워커 전용 실행기가 섞여 있다. 역할에 맞추려면 도메인 패키지를 재배치해야 한다.
`@ConfigurationPropertiesScan`은 컴포넌트 스캔과 별도 경로로 Properties를 등록하므로 패키지 스캔만으로 역할 전용 Properties를 격리하지 못한다.
메인 애플리케이션의 `com.moeum` 전체 스캔과 역할별 스캔도 겹친다.

### 모듈 소유 역할 설정

각 모듈이 `ConversationWorkerConfiguration` 같은 역할 설정을 소유하고 역할 전용 클래스를 `@Import`한다. 조건은 설정 클래스에만 둔다.
클래스 단위로 지정하므로 도메인 패키지를 유지하고, 역할별 빈 목록이 설정 클래스에 드러난다.

실험으로 확인한 제약은 다음과 같다.

- `@Component`·`@Configuration` 같은 스테레오타입이 남은 import 대상은 역할 설정이 꺼져도 메인 스캔으로 등록된다. import와 스캔이 겹치면 정의가 하나로 합쳐져 격리가 조용히 깨진다.
- 컨트롤러는 MVC 핸들러 인식에 `@RestController`가 필요하므로 메인 스캔에서 `@Controller`·`@ControllerAdvice`를 제외해야 한다.
- `@ConfigurationPropertiesScan`은 `@ConditionalOnRole`을 평가한다. 역할 전용 Properties는 조건을 유지하면 격리된다.
- import한 일반 클래스에도 `@Scheduled`와 `@Transactional` 후처리가 적용된다. 스테레오타입을 떼면 kotlin-spring이 클래스를 열지 않으므로 메서드에만 `@Transactional`을 둔 클래스는 직접 열어야 한다.

빈 하나의 등록 이유를 알려면 모듈 설정·역할 설정·공통 스캔·Properties 스캔을 모두 확인해야 한다. 구성의 중앙화가 등록 경로의 단순화는 아니다.

## 판단

역할은 셋으로 안정적이고 단기 확장은 API 추가다. 새 컨트롤러의 등록 비용은 어노테이션 한 줄과 import 한 줄로 같다.
전환의 이득은 구성 가독성이고, 대가로 메인 스캔과 모든 역할 전용 빈의 등록 경로를 바꾼다.
빈 단위 지정을 유지하고 지정 누락과 설정 격리를 테스트로 보호한다.

서비스 분리의 축은 실행 역할이 아니라 도메인이다. 분리 비용의 중심은 모듈 간 호출·데이터 소유권·트랜잭션 경계다.
빈 등록 방식은 분리할 때 정리할 설정이며 분리를 막는 결합이 아니다.

## 보호 장치

ExecutionRoleRulesTest는 HTTP 진입점·서블릿 Filter를 API 역할로, `@Scheduled` 클래스와 LlmClient·LlmProvider 구현을 워커 역할로만 지정하도록 강제한다.
`@Configuration`의 `@Bean` 메서드와 공통 빈은 대상이 아니다. 이벤트·메시지 리스너 같은 새 진입점 종류는 규칙에 추가한다.

WorkerRoleIsolationIntegrationTest는 local 프로필·OS 환경변수·시스템 속성 없이 각 역할을 기동한다.
역할별 필수 빈의 등록과 다른 역할 빈의 미등록을 검사한다.
다른 역할의 설정이 없거나 무효여도 기동하는지, 같은 무효 값이 해당 역할에서는 기동을 거부하는지 함께 확인한다.
모든 역할을 한 프로세스에서 켜는 조합은 local-all 기반 통합 테스트가 실행한다.

## 재검토 조건

- 새 실행 역할이나 새 진입점 종류(메시지 소비자·아웃박스 발행기 등)가 추가된다.
- 도메인 모듈을 별도 프로세스로 분리한다. 분리 서비스의 bootstrap을 구성할 때 모듈 소유 역할 설정을 함께 검토한다.
- 역할 지정 누락이나 잘못된 등록이 테스트를 통과해 실제 문제로 이어진다.
