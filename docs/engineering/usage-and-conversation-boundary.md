# 사용량 경계와 연속 입력

## 사용량 기간의 선택

초기 서버는 사용자별 UTC 날짜에 새 메시지 사용량을 집계하고 UTC 자정에 초기화했다. 한국에서는 오전 9시에 한도가 바뀌므로 일기를 쓰는 사용자의 하루와 어긋났다.

사용자는 새 메시지 횟수 한도를 **RecordDay마다 제공**하는 방향을 선택했다. 여행으로 기존 기록이 일찍 마감돼도 새 기록에는 한도를 다시 제공한다. 짧은 간격으로 한도가 다시 생길 수 있지만 드문 여행 상황의 허용 가능한 비용으로 판단했다.

기록의 USER 원본 수는 기존 `sourceRevision`으로 알 수 있으므로 같은 수치를 별도 컬럼에 다시 저장하지 않는다. 접수 트랜잭션은 이미 사용자 상태·열린 기록을 잠그므로 이 값으로 한도를 검사할 수 있다. 분당 접수 속도 제한은 기존 사용자별 행과 원자적 갱신으로 유지한다.

`/quota`는 열린 기록의 원본 수와 예약 마감 시각을 반환한다. 열린 기록이 없거나 예약 마감이 지났으면 사용량은 0이고 `resetAt`은 null이다. 다음 메시지의 장소를 받기 전에는 새 기록의 마감 시각을 계산할 수 없기 때문이다. 화면에 초기화 시각을 표시할지는 아직 정하지 않았다.

PostgreSQL 통합 테스트는 기록당 한도 재제공, 동시 접수, 분당 제한, 여행 중 거절의 롤백, 빈 기록의 응답을 검증했다. 실제 공급자 비용과 사용자 경험은 이 검증에 포함되지 않는다.

무료 20회·구독 100회, 메시지당 4,000자, 사용자별 분당 새 메시지 60회는 확정된 현재 수치이며 서버 설정으로 변경할 수 있다. 기록당 한도로 바꾸더라도 분당 접수 제한은 유지한다.

## 연속 입력의 응답 시점

현재 서버는 사용자 메시지마다 AI 답변 작업을 하나씩 만들어 순서대로 처리한다. 사용자가 AI 답변을 읽기 전에 다음 메시지를 보내면 대화가 엇갈려 보일 수 있다.

화면 개발과 함께 짧은 대기와 최대 대기 시간을 두고 연속 입력을 모아 답하는 방향을 구체화한다. 작성 중 신호는 필요성이 확인되면 대기를 조정하는 보조 판단에 사용한다. 대기 시간과 묶음 기준은 아직 정하지 않았으며, 현재 서버는 이 방식으로 동작하지 않는다.
