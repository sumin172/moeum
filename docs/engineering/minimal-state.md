# 필요한 상태와 관행적으로 추가한 데이터 구분하기

## 문제

기능별로 스냅샷·메타데이터·활성 포인터·이력을 추가하면 개별 구현은 편해진다.
하지만 소비처가 사라진 뒤에도 매핑·갱신·테스트가 그 구조를 붙잡을 수 있다.
저장량뿐 아니라 DB 왕복과 일관성 관리 경로도 증가한다.

사용자가 제시한 기준은 비즈니스 프로세스까지 정규화하는 것이다.
기존 자원으로 충분하면 재사용하고, 계산 가능한 상태를 추가 저장하는 것은 성능 근거가 있을 때 검토한다.
진단·정보성 데이터 추가는 관행이 아니라 별도 동의 대상이다.

## 적용한 판단

| 대상 | 판단 근거 |
|---|---|
| 활성 기록 ID | 사용자별 열린 기록 유일 인덱스로 조회할 수 있는 중복 포인터 |
| 일기 입력 동결 버전 | 마감 기록과 마지막 USER 순번으로 같은 입력을 결정 가능 |
| 일기 확정·리비전·JSON 본문 wrapper | 사용자 확정 없이 바로 보관하는 정책이며 이력 조회·복원 소비처가 없음 |
| 모델·프롬프트·토큰·시도 ID의 결과 컬럼 | 업무 처리보다 진단 목적이며 로그·메트릭에서 조사 가능 |
| 마감·세션 사유와 미사용 삭제 시각 | 현재 기능에서 판단하거나 집행하는 소비처가 없음 |
| 완료 작업의 결과 ID | 결과 저장과 작업 완료가 원자적이며 결과 유일키로 존재 확인 가능 |

이메일은 사용자 판단에 따라 유지했다.
반면 원본 순번·스트림 순번·작업 version·리스·접수 사용량은 실제 순서·중복 방지·복구·한도 집행에 사용한다.
컬럼 수 자체를 줄이는 것과 필수 업무 상태를 제거하는 것은 다르다.

## 코드 정리에서 얻은 교훈

GenerationJob의 운영 생성은 SQL INSERT였지만 테스트가 별도 운영 팩토리를 사용했다.
단순 참조 검색은 이를 “사용 중”으로 분류할 수 있다.
생성 fixture를 테스트 소스에 두면 실제 운영 경로와 검증용 구성의 책임이 드러난다.

모든 삭제를 포트폴리오 사례로 남길 필요는 없다.
중요한 것은 소비처·실패 보장·DB 비용을 기준으로 판단한 과정이다.
현재 기준은 [개발 원칙](../PRINCIPLES.md)에 있다.
