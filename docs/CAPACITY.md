# 성능 시험 기준

시험은 목표 처리량·데이터 크기·실행 시간·자원 예산을 지정해 수행한다.
수치는 시험 기준이며 실제 사용자 수 예측이나 제품의 생성 완료 약속과 별개다.
확인된 범위는 [검증 현황](CAPACITY_RESULTS.md), 명령과 설정은 [시험 절차](CAPACITY_RUNBOOK.md)에 있다.

## 프로파일과 판정

| 프로파일 | 기본 요청률 | 사용 목적               |
|----------|------------:|-------------------------|
| P0       |      25 RPS | 기능을 포함한 작은 부하 |
| P1       |     250 RPS | 현재 단기 용량 평가     |
| P2       |   2,500 RPS | 확장 한계 탐색          |

현재 P1의 통과한 시험 길이는 구간당 60초다. P2는 실행 결과가 없는 미검증 프로파일이다.
3분 시험은 별도 결과로 보고한다. 장시간·대규모 프로파일은 실행 조건을 정한 뒤 평가한다.

## 시험별 목적과 판정

| 시험                         | 목적                         | 성능 목표 판정                           |
|------------------------------|------------------------------|------------------------------------------|
| benchmark P0·P2              | 처리량·지연 측정, 한계 탐색  | 보고만 한다                              |
| benchmark P1                 | 단기 용량 평가               | 목표 미달이면 실패                       |
| sustained                    | 목표 부하 확인               | 프로파일과 관계없이 목표 미달이면 실패   |
| failure                      | 장애 재시도·종료 복구 확인   | 성능 목표는 판정하지 않고 복구만 판정    |
| RetentionCapacityTest        | 운영 주기 정리의 균형과 회복 | 아래 운영 주기 정리 기준으로 판정        |

모든 시험에서 접수 원본 유실·중복 응답·중복 일기는 실패다.
주입기가 예정 요청을 보내지 못한 경우(`generatorRejected`)는 부하를 만들지 못한 도구 실패이며 목적과 관계없이 실패다.
접수 HTTP 오류와 응답 미완료는 서버의 측정 결과다. 성능 목표를 판정하는 시험에서는 실패이고, 측정 목적 시험에서는 단계별 `injection`(예정·전송·드롭)과 `httpStatuses`(상태별 수, 0은 전송 오류)로 원인을 나눠 보고한다.

failure의 장애 주입은 대화 실행 주기마다 첫 시도에만 실패시킨다. 기록당 실행 주기는 여러 번일 수 있으므로 주입 수를 작업 수가 아니라 재시도로 완료된 응답 수와 비교한다.
주입 전후 진행 중 실행이 없음을 확인하고, 장애 주입 발생·미응답 입력 0·중복 응답 0·마지막 실행 주기의 재시도 1회 완료를 각각 판정한다.

### 운영 설정과 다른 시험 설정

| 설정                       | 시험                     | 운영 기본                            |
|----------------------------|--------------------------|--------------------------------------|
| 대화·일기 poll             | 0.05초·0.1초             | 1초·1초                              |
| 대화 backoff               | 1·2초                    | 10·60초                              |
| 일기 backoff               | 1·2·4·8초                | 1분·5분·30분·2시간                   |
| 429 최소 대기              | 2초                      | 대화 1분·일기 5분                    |
| 공급자 동시 호출 상한      | 실행 슬롯과 같게         | 대화 8·일기 2                        |
| 종료 대기                  | 2초                      | 10초                                 |
| 생성·전달 리스             | 운영과 같음(5분·1분)     | 5분·1분                              |

현재 운영 기본 poll·backoff로 실행하는 시험은 없다. 시험의 대기·지연 결과를 운영 기본 설정의 성능으로 해석하지 않는다.

| 측정 항목             | 시험 기본 목표                               |
|-----------------------|----------------------------------------------|
| 메시지 저장 API       | p95 ≤ 300ms, p99 ≤ 1초                       |
| API 서버 오류         | 0.1% 미만                                    |
| 대화 작업 대기        | p95 ≤ 2초                                    |
| 혼합 부하의 API 지연  | 메시지 저장 API 목표와 같음                  |
| 접수·저장·완료 무결성 | 접수 원본 유실·중복 결과·수정본 덮어쓰기 0건 |

주입기 드롭과 실제 접수 수를 함께 평가한다.
AI 실행 지연은 작업 대기와 별도로 보고한다.
일기는 대상 수·실제 호출 수·마감부터 완료까지의 지연과 backlog 해소를 측정한다.
대화 단독 대비 혼합 부하의 API p95 증가율(`journalApiP95IncreaseFraction`)은 보고만 한다. 기준 p95가 수십 ms이면 몇 ms 차이로 크게 변해 성능 문제와 측정 변동을 구분하지 못한다.

## 시험 자원

API·대화·일기는 별도 JVM과 DB 풀을 사용하며 PostgreSQL은 공유한다.
보고서에는 슬롯·풀·replica·poll 간격·DB CPU/메모리·JVM heap·fake 지연을 기록한다.
누적 데이터 수와 메시지 길이·사용자 분포·타임존·첫 기록 생성량을 명시한다.

필요한 공급자 동시 호출 수의 근사치는 요청률 × 평균 호출 시간이다.
DB 연결 예산은 각 역할의 최대 replica × pool의 합이다.
실제 공급자의 동시 호출·RPM·TPM·비용은 별도 확인 대상이다.

## 검증 항목

- 대화 단독, 워커 증설, 일기 생성과 정리 동시 실행.
- 예정·전송·접수·완료 수와 주입기 드롭.
- API 지연, 작업 대기, DB 풀 대기·잠금, heap·GC·CPU.
- 429·timeout·5xx 재시도, 실제 일기 워커 종료와 리스 회수.
- 전달 등록 직전·직후 종료의 멱등 복구.
- 수정 권한·version 충돌·마감 후 다음 기록 귀속.
- 누적 원본·완료 작업 정리의 처리량과 보관 크기.
- 최대 정상 일기 입력의 모델 한도와 동시 메모리.

시험 길이와 데이터 크기를 늘리는 작업은 별도 범위로 정한다.
fake 공급자 결과와 실제 모델 품질·할당량을 구분한다.

## 실제 모델 품질과 운영 정리의 한정 검증

품질 사례는 장소 정정, 짧은 부정과 미확정 결과, 계획 취소와 실제 행동의 구분이다.
3개 사례를 실제 대화·일기 생성기로 각각 2회 생성한다. 호출 성공·형식 검증과 기대 사실의 수동 검토를 나눠 보고한다.
실패 호출은 성공 표본에서 제외하되 전체 시도와 오류 유형을 보존한다. 후속 성공으로 최초 실패를 통계에서 지우지 않는다.
실제 공급자 검증은 설정된 기본 경로([AI 공급자](LLM.md))에서 같은 입력·평가 기준으로 수행한다.
수용 범위와 모델별 한도·실사용자 수 계산은 [검증 현황](CAPACITY_RESULTS.md)을 따른다. 계산상 인원과 실제 공급자 검증 결과는 구분한다.

운영 주기 정리 시험은 30분·API 25 RPS·과거 기록 10,000개로 범위를 정한다.
운영 정리 스케줄러를 사용하고 만료 응답·일기 작업을 별도로 주입하며, 시험 중 일기 워커를 60초 중단하고 재시작한다.
자원 조건과 주입량은 [실행 절차](CAPACITY_RUNBOOK.md)를 따른다.
합격 기준은 기존 절대 API·응답 대기 목표, 접수·응답 완료, 만료 작업 적체 최종 0건, 원본과 보존 기간 전 작업 유지다.
정리 정확성은 운영 정리 조건의 복제로 판정하지 않는다. 주입한 만료 작업 ID가 모두 삭제됐는지, 오래됐지만 정리 조건 밖인 작업(열린 기록의 완료 작업, 먼 미래 예약의 PENDING, 유효 리스의 PROCESSING, 최근 생성된 일기 실패)이 같은 상태로 남는지를 ID로 확인한다.
원본 유지는 fixture·접수 USER 수로 확인한다. 시험 중 생성된 ASSISTANT는 기록별 마지막 답변 경계와 중복 응답으로 확인하며, 중간 ASSISTANT의 개별 유실은 검출하지 않는다.
초기 3분 이후 응답 작업 적체는 40초 유입량(52건) 이하로 제한한다. 주입 종료 후 회복 대기는 180초다.
이 시험에는 정리 없는 기준선과의 상대 p95 비교가 없으며 실제 30일 경과나 장기 디스크 평형을 검증하지 않는다.
