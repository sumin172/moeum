# 부하 격리와 6개월 성장 검증

상태: 측정 계획. 아래 수치는 사용자 수 예측이나 현재 처리 성능이 아니다.
실제 공급자 할당량·운영 DB·비용 예산은 미확정이다.
출시 용량은 측정 결과와 외부 공급자 용량을 모두 만족하는 범위로 발표한다.

## 검증 규모 기본안

사용자당 하루 사용자 메시지 평균 20개, 활동 사용자당 일기 1개, 피크/평균 약 10배를 가정한다.
20개는 부하 계산용 평균이며 무료·구독 요금제의 확정 한도가 아니다.
무료·구독의 유한한 대화 한도와 구독 비율을 시험 입력에 명시하고 높은 구독 한도에서 긴 대화도 검증한다.
DAU는 가입자 수가 아니다. 대화가 많은 사용자와 길이가 긴 원본도 별도 분포로 넣는다.

| 프로파일 |       DAU |  메시지/일 | 평균 저장 RPS | 피크 저장 RPS 목표 |   일기/일 |
|----------|----------:|-----------:|--------------:|-------------------:|----------:|
| P0       |    10,000 |    200,000 |           2.3 |                 25 |    10,000 |
| P1       |   100,000 |  2,000,000 |          23.1 |                250 |   100,000 |
| P2       | 1,000,000 | 20,000,000 |         231.5 |              2,500 | 1,000,000 |

P0는 첫 검증, P1은 초기 확장 승인 목표, P2는 병목 탐색 목표다.
P2를 통과하지 않고 백만 DAU를 지원한다고 주장하지 않는다.
6개월 목표 DAU를 확인하면 해당 프로파일과 인프라 예산을 조정한다.

## 사용자 체감 목표 기본안

공급자가 정상이고 필요한 할당량을 확보한 시험에서 다음을 목표로 한다.

- 메시지 저장 API: p95 300ms 이하, p99 1초 이하.
- 메시지 저장 서버 오류율: 0.1% 미만. 입력 오류·명시적 quota 응답은 별도 집계.
- 대화 작업 대기 시간: p95 2초 이하. LLM 실행 시간은 별도로 기록.
- 일기: 마감 후 60분 이내 99% 생성. 공급자 장애 중 지연은 별도 표시하되 복구 뒤 backlog 해소 시간을 측정.
- 저장 성공으로 접수한 원본의 유실·남의 데이터 조회·중복 결과 저장·수정본 덮어쓰기: 0건.
- 생성 입력 확정 후 미접수 원본의 정책상 폐기는 저장 후 유실과 별도로 집계한다. 폐기 때문에 AI 호출·작업이 늘어나지 않아야 한다.
- Journal 부하 추가 시 저장 API p95 증가: 대화 단독 기준 대비 20% 이하이며 절대 지연 목표도 만족.
- 정상 공급자에서 대화 최종 지연은 대기+LLM 지연+저장으로 보고한다. 외부 호출 시간을 숨기지 않는다.

실측 p99를 기준으로 리스와 타임아웃을 설정한다.
일기 60분 목표는 초안 가정이다. 더 짧은 약속에는 그에 맞는 공급자/워커 용량이 필요하다.

## 공급자 용량 산식

동시 호출 필요량은 대략 다음과 같다.

동시 호출 수 = 초당 완료 목표 × 평균 호출 시간
분당 토큰 = 분당 호출 수 × 호출당 평균 입력/출력 토큰

예: 100,000건을 1시간에 처리, 호출당 10초라면 27.8건/초와 약 278 동시 호출이 필요하다.
이는 하한 추정이다. 재시도·지연 분산·토큰 제한을 고려해 최소 1.5배 여유를 검토한다.
100,000건이 한 시간대에 몰리지 않는다는 가정은 실제 지역별 분포로 검증한다.
긴 기록 입력 토큰을 포함해 RPM/TPM·비용을 계산한다.
워커만 늘려 공급자 한도를 초과하는 것을 확장으로 취급하지 않는다.

## 자원 격리 계약

- API, conversation-worker, journal-worker의 배포 수와 DB pool 상한을 독립 설정한다.
- DB 최대 연결 수보다 각 역할의 최대 replica × pool 합계가 작아야 한다.
  관리·마이그레이션·복구 연결 여유도 별도로 둔다.
- 단일 provider를 공유해도 대화/일기 실행 슬롯을 구분하고 대화 처리 용량을 우선 확보한다.
- 고정 replica 상한 단계에서는 전체 호출 예산을 역할/인스턴스에 나누어 배정한다.
- 동적 autoscaling을 도입하기 전에는 replica 증가에 맞춘 전역 호출 제한 수단을 마련한다.
  별도 키가 동일 공급자 프로젝트 한도를 공유하는지도 확인한다.
- Journal 워커가 대기할 때 API의 DB 커넥션을 점유하지 않는다.
- 배치 원본 조회는 recordDay 단위이며 한 번에 전체 사용자 본문을 적재하지 않는다.
- 대화 입력 예산은 DB 조회 단계부터 제한한다.
- 일기 입력이 단일 호출 한도를 넘으면 원문을 조용히 자르지 않는다.
  초기에는 명시적인 생성 제한/실패 상태와 원본 보존을 제공한다.
  정상 사용에서 이 제한이 발생하면 출시 전에 입력 처리 전략을 다시 설계한다.
- 실행 가능한 슬롯만큼 선점한다. 가상 스레드 무제한 생성이나 긴 선점 대기열로 부하를 숨기지 않는다.

Spring의 virtual-thread scheduler에서도 fixed-delay 실행 경로는 주의가 필요하다.
스케줄러에서 외부 호출을 분리하는 설계는 프레임워크 기본값과 무관하게 유지한다.
참고: [Spring scheduling](https://docs.spring.io/spring-framework/reference/integration/scheduling.html).

## 시험 구성

1. 실제 PostgreSQL과 Flyway 신규 스키마, 실제 HTTP·인증 필터·작업 선점 경로를 사용한다.
2. LLM은 제어 가능한 fake provider로 시작한다. 정상 지연 1/10/30초, timeout, 429, 5xx를 주입한다.
3. 워밍업 10분, 목표 부하 30분, 마감 집중 backlog 처리, 최소 2시간 지속 시험을 분리한다.
4. 메시지 길이·사용자별 편중·타임존·하루 기록 수·동시 로그인 기기를 보고서에 기록한다.
5. 공급자 실제 스모크/할당량 확인은 별도로 수행한다. fake provider 통과를 외부 공급자 용량 검증으로 보고하지 않는다.
6. 초기 빈 DB뿐 아니라 보존 정책에 따른 6개월 예상 누적량으로 조회·인덱스·정리 비용을 검증한다.
   P1 가정만으로도 사용자 원문이 약 3.6억 건/180일이다. assistant와 인덱스·백업 용량은 추가다.
   이 규모의 시험을 하지 못했다면 검증한 데이터 크기를 보고하고 P1 6개월 보장을 유보한다.

## 필수 시나리오

| 시험                                      | 관측/성공 조건                                |
|-------------------------------------------|-----------------------------------------------|
| 대화 단독 피크                            | 저장 지연·대화 대기·DB 풀 기준선              |
| 일기 100% 한 시간 마감 + 대화 피크        | 대화 지연 격리, backlog 감소율·완료 시간      |
| Journal 워커 전부 종료/재시작             | API 영향 제한, 마감/작업 누락 없이 회수       |
| LLM 429/timeout                           | 제한된 재시도, 무한 폭증 없음, 원본 저장 유지 |
| 1→N 워커 증가                             | DB 연결·공급자 총량 준수, 실제 처리량 증가    |
| 같은 사용자 연속 발화·여러 기기           | 사용자별 순서, 중복 결과 없음                 |
| 전달 등록 직전/직후 종료                  | 중복 전달 허용, 중복 생성 요청 없음           |
| 리스 만료 후 늦은 결과                    | fencing으로 결과 저장 거부                    |
| 생성 중 수정/지연 원본 | 수정본 보호, 입력 확정 후 원본 폐기·자동 갱신 없음 |
| 기존 작업 FAILED로 변경, 신규 메시지 없음 | 상태 조회에 실패 반영                         |
| 관측 수집기 중단                          | bounded buffer·유실 계측, 업무 처리 유지      |
| 작업 정리 배치 + 대화 피크                | 활성 작업 보존, 삭제 부하 상한 준수           |

한도 소진·잔여 1회 동시 요청에서는 한도 초과 원본 미저장, 단일 차감과 현재 잔여 횟수 반환을 확인한다.
구독 변경은 기간 사용량 유지·새 한도 적용을, 실패 복구 재시도는 추가 차감 없음을 확인한다.

측정: 요청 지연, 작업 대기/실행 시간, oldest pending age, lease 회수 수, 오류 분류,
DB 쿼리 수·반환 행/바이트·풀 대기·잠금 대기, CPU/메모리/GC, LLM 호출/토큰량.
ID는 로그 상관관계에 쓰고 메트릭 label에는 넣지 않는다.

## 확장 판단

- 대화 지연이 batch DB 읽기/쓰기와 함께 악화: batch 동시성 축소·쿼리/인덱스 개선부터.
- 작업 상태 갱신이 DB의 지배적 비용: 관리형 큐 이전 검토. DB와 큐 사이 전달 보장도 함께 설계.
- 호출 한도 포화: 공급자 할당량/일기 완료 약속/가격을 조정. replica 추가로 해결하지 않음.
- 데이터 증가로 hot query 성능 악화: 실제 실행계획을 근거로 인덱스·보존·파티셔닝 검토.
- 공유 DB 격리 한계가 측정됨: Journal 저장소/읽기 경로 분리 검토. replica 읽기 지연과 원본 버전 일관성 검증 필요.

보고서에는 하드웨어·DB 크기·설정·공급자 가정·실행 버전·성공/실패 수·병목을 함께 남긴다.
현재 이 문서에 기록된 성능 측정 결과는 없다.
