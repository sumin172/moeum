# R6 측정 결과

2026-10-18 로컬 Windows / Java 21.0.8 / Docker Desktop에서 측정했다.
실행 방법은 [시험 절차](CAPACITY_RUNBOOK.md), 목표는 [부하 기준](CAPACITY.md)을 따른다.
아래 수치는 접수 시각 귀속으로 재구성하기 전 실행의 결과다. 해당 구조의 단기 P1 부하·실제 리스 복구·일반 회귀를 통과했으며, 현 구조의 성능 승인은 재측정이 필요하다. 장시간·6개월 누적량·실제 공급자 용량 승인도 남아 있다.

## 시험 범위

- API·대화 워커·일기 워커는 각각 별도 JVM(Xmx 512MiB), PostgreSQL 17은 4 CPU / 4GiB / shared_buffers 256MiB다.
- 누적 데이터: 기록 50,000개, USER 1,000,000개, ASSISTANT 999,500개. 180일로 분산한 합성 데이터다.
- P1: 250 RPS, 워밍업 30초, 구간당 60초. 대화 fake 지연 1초, 일기 fake 지연 10초다.
- 대화 슬롯 320/인스턴스, DB 풀 12/인스턴스, 일기 슬롯 48·DB 풀 4다. 대화 워커 1→2대를 비교한다.
- 시험 poll은 대화 50ms·일기 100ms다. 운영 기본 poll 1초와 다른 설정이다.
- HTTP 입력은 10% 4,000자·20% 200자·70% 1,000자이며, 합성 사용자 약 10%가 구독자다. 5개 타임존을 사용자별로 고정하고 사용자당 18회 이하를 보낸다.
- open-loop 주입에서 예정 요청을 버린 수를 별도로 집계한다. 일부 요청만 접수한 결과를 250 RPS 통과로 보지 않는다.

## 확인한 병목과 현재 구현

당시 기존 기록 저장은 사용자 상태 INSERT 충돌 검사, 이미 잠근 활성 기록의 재조회,
신규 응답 작업의 merge 존재 확인을 반복했다. 이 중복 접근을 줄이고 신규 작업은 persist로 저장했다.
이후 활성 기록 ID 컬럼을 제거하고 열린 기록 유일 인덱스로 조회하도록 변경했으므로, 당시 DB 접근 수와 지연 수치를 현재 구현의 실측치로 간주하지 않는다.

대화 선점은 남은 실행 슬롯을 먼저 예약한 뒤 최대 32개를 한 트랜잭션에서 확보한다.
인스턴스마다 선점 트랜잭션은 하나만 진행한다. DB 후보 조회·커밋을 작업마다 반복하지 않는다.
기록 잠금 뒤 새로운 READ COMMITTED 문장에서 선두를 다시 검사하므로 동시 재시작과 순서 보장을 유지한다.
실행 대기열을 두지 않고, 예약 슬롯 이내에서만 리스를 시작한다.
이전 건별 선점 진입점과 동시 선점 설정은 제거했다.

## P1 비교

API 풀 16, 같은 DB 사양과 데이터 크기에서 순차 실행했다. 반복 실험의 신뢰구간을 구한 결과는 아니다.

| 조건                            | 대화 워커 |     접수 / 예정 |   API p95 |   API p99 | 작업 대기 p95 |
|---------------------------------|----------:|----------------:|----------:|----------:|--------------:|
| API 중복 조회 제거 전·건별 선점 |         1 | 13,288 / 15,000 | 3,528.8ms | 4,540.1ms |    51,015.9ms |
| API 중복 조회 제거 후·건별 선점 |         1 | 15,000 / 15,000 |   234.0ms |   475.2ms |    17,087.4ms |
| API 중복 조회 제거 후·배치 선점 |         1 | 15,000 / 15,000 |   317.6ms |   952.6ms |     1,424.5ms |
| API 중복 조회 제거 후·배치 선점 |         2 | 15,000 / 15,000 |   373.8ms |   570.6ms |       158.3ms |

배치 선점 시험은 두 구간 모두 접수한 작업을 전부 완료했다. API p95 300ms 목표는 미달했다.
초기 새 기록 생성 구간의 API 풀 대기가 확인돼 API 풀 24로 재시험했다. DB 사양과 나머지 예산은 유지했다.

| API 풀 24·배치 선점                 |     접수 / 예정 | API p95 | API p99 | 작업 대기 p95 |
|-------------------------------------|----------------:|--------:|--------:|--------------:|
| 대화 워커 1대                       | 15,000 / 15,000 | 107.3ms | 271.7ms |       448.7ms |
| 대화 워커 2대                       | 15,000 / 15,000 | 239.5ms | 663.5ms |       464.9ms |
| 대화 워커 2대 + 일기 1,000건 + 정리 | 15,000 / 15,000 | 192.1ms | 256.7ms |       216.6ms |

세 구간 모두 접수한 작업을 전부 완료하고 API·작업 대기 목표를 통과했다.
일기 추가 시 API p95는 이번 실행에서 19.8% 낮아 20% 증가 상한도 충족했다. 일기가 성능을 개선한다는 인과 증거로 해석하지 않는다.
일기 1,000건 모두 마감 후 243.1초 이내 생성됐다(p95 232.9초). 혼합 구간에서 완료 작업 11,268건을 정리했다.
무료 수정 403·구독 수정 200·stale version 409를 확인했다. 당시 생성 메타데이터 보존과 늦은 원본 폐기 검증은 현재 설계에 적용되지 않는다.
전체 DB의 중복 응답·중복 일기는 0건이었다. [통과 원자료](capacity/p1-batch-api24.json).
API 풀 16 배치 시험의 단일 워커 DB CPU 제한 정지는 0회, 두 워커 구간은 601개 quota 기간 중 4회였다.
CPU 제한이 주된 원인이라는 증거는 없다. WAL 대기와 커넥션 경쟁은 별도로 관찰한다.

원자료: [조회 감소 비교](capacity/p1-query-reduction-comparison.json), [배치 선점·API 풀 16](capacity/p1-batch-api16.json).
배치 보고서의 SQL 상위 통계는 부하 주입 구간의 차이다. 이전 비교 파일은 지연·접수 결과만 보존했다.

## 장애 복구

별도 failure 시나리오에서 다음을 확인했다. [원자료](capacity/failure-recovery.json).

- 429·timeout·5xx 각각 첫 시도 실패 25건을 주입했고, 각 25건 모두 2회 이내 시도로 완료했다.
- 일기 JVM을 실제 종료해 PROCESSING 2건을 남겼다. 재기동 뒤 운영의 5분 리스 만료로 회수해 시험 일기 3건을 모두 완료했다. 재기동 준비 후 완료까지 276.8초였다.
- 일기 워커가 없는 동안 별도 대화 25건을 모두 접수·완료하고 원본 소유자/클라이언트/기록 귀속을 확인했다.
- 전달 선점 후 등록 전·등록 직후에 각각 Runtime.halt(91)했다. 실제 1분 리스 뒤 두 경우 모두 delivery_version 2·acknowledged true, 작업 1건·일기 1건으로 복구했다.
- 중복 응답·중복 일기는 0건이었다.

이 짧은 시험은 복구 동작 검증이다. 동일 기록에 입력이 빠르게 몰린 구간의 대기 목표는 실패했으며 P0 용량 통과로 세지 않는다.
성능 주입·워커 종료 중 대화 검사가 끝난 뒤, 5분 리스 대기 중에 전체 회귀를 병행했다. 이 시나리오의 지연값은 용량 승인에 사용하지 않는다.

## 일반 회귀와 공급자

일반 백엔드 회귀 161개가 실패·오류·생략 0개로 통과했다. [모듈별 집계](capacity/regression-summary.json).
capacity·provider-smoke 태그는 일반 회귀에서 제외한다.
공급자 스모크 작업은 실행했지만 GEMINI_API_KEY가 없어 테스트 1건을 생략했다. 실제 공급자 호출/할당량을 통과한 것으로 세지 않는다.

## 승인하지 않은 범위

P2, 30분 목표 부하·2시간 지속 시험, 실제 공급자 RPM/TPM/비용, 운영 인프라는 이 단기 결과로 승인하지 않는다.
원본 100만 건 시험은 P1 180일 원본 약 3.6억 건과 다르다. 6개월 누적 데이터의 인덱스·보관·백업 용량은 미검증이다.
fake provider 장애는 업무 재시도·복구를 검증하며 실제 공급자 네트워크·회로 차단기의 동작을 대체하지 않는다.
