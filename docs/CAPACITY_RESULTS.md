## 무료 API 한도와 베타 규모 계산

확인 기준은 2026-10-24 Default Gemini Project의 AI Studio 모델별 한도 화면이다. 공급자 한도는 프로젝트·모델·등급에 따라 달라지므로 배포 시 표시값을 따른다.

| 모델                  | RPM (분당 요청) | TPM (분당 입력 토큰) | RPD (일일 요청) | 검증 상태                                                                       |
|-----------------------|----------------:|---------------------:|----------------:|---------------------------------------------------------------------------------|
| Gemini 3.1 Flash Lite |           약 15 |           약 250,000 |             500 | 확정·기본 모델. 짧은 사례·두 최대 입력 성공 표본 확보, 실패·품질 제약 함께 기록 |

[공식 한도 안내](https://ai.google.dev/gemini-api/docs/rate-limits)에 따라 한도는 API 키가 아닌 프로젝트 단위로 적용하며 모델별 제한을 함께 확인한다.
RPD 초기화는 태평양 자정이며 사용자의 기록 마감·사용량 구간과 별개다. 명시된 한도와 실제 가용성은 동일한 보장이 아니다.

### 하루 실사용자 수

계산 가정은 한 사람이 하루 기록 하나에 메시지를 보내고 메시지마다 AI 응답 한 번, 기록마다 일기 생성 한 번을 호출하는 것이다.
대화·일기 모두 3.1 Flash Lite를 사용하는 경우의 요청 수만 계산하며 재시도·개발 호출은 기본 호출 수에 포함하지 않는다.
30% 여유는 계산용 가정이며 서버에 추가한 제한이나 확정된 비용 정책이 아니다.

| 한 사람의 하루 대화 | 일기 포함 호출 수 | RPD 500의 이론상 인원 | 30%를 남긴 계획 인원 |
|---------------------|------------------:|----------------------:|---------------------:|
| 5회                 |               6회 |                  83명 |                 58명 |
| 10회                |              11회 |                  45명 |                 31명 |
| 20회                |              21회 |                  23명 |                 16명 |

인원은 floor(사용 가능한 RPD / 사용자당 호출 수)로 계산한다. 가입자·접속자 수가 아닌 하루 실사용자 수다.

### 동시 사용과 토큰 한도

동시 사용은 분당 실제 AI 요청 수·입력 토큰 수로 계산한다. RPM은 동시 접속자 수나 동시 실행 슬롯 수가 아니다.
3.1 Flash Lite에서 5명이 각각 30초마다 한 번씩 요청하면 대화만 분당 10회이며, RPM 약 15회에서 일기·재시도·추가 요청의 여유는 약 5회다.
이 예시는 TPM과 잔여 RPD가 충분하다는 가정이며 동시 사용 5명을 실측으로 승인한 결과는 아니다.

대화 입력에는 이전 문맥도 포함되므로 메시지 길이·대화 진행 정도가 TPM 수요에 영향을 준다. 같은 시각에 마감하는 일기들의 요청·토큰도 합산한다.
3.1 Flash Lite의 구독 최대 입력은 256,754토큰으로 관측됐다. 표시된 TPM 약 250,000과 비슷하거나 크므로 단일 호출 성공을 반복 호출 가능성이나 무료 티어 처리량의 보장으로 해석하지 않는다.
하루 대화 10회 패턴의 실사용자 20~30명은 계획값이며 일일 요청·분당 요청·토큰·실제 품질을 함께 확인한 뒤 확정한다.
Fake AI 서버·DB 시험의 25 RPS는 공급자의 무료 API 처리량과 구분한다.

짧은 사례의 핵심 사건·부정·정정은 반영됐다. 다만 계획 변경 사례에서 사용자에게 근거가 없는 제목의 '데이트', 본문의 '아쉬운 마음'이 관측됐다. 결과 생성 성공과 사실 충실도는 별개의 판정이다.

두 최대 입력의 성공 결과는 서울숲으로의 장소 정정, 발표 완료, 민지와 버섯 파스타·안도감을 반영했고 팀장의 칭찬을 사실로 추가하지 않았다. 구독 최대 결과는 칭찬에 대한 부정을 별도로 서술하지는 않았다.

구독 최대 입력에서 관측한 생성 실패는 검사 단계와 원인이 미확정이며 동일 조건에서 재현되지 않았다. 시험 보고서는 생성기의 고정 실패 메시지를 journalValidationFailure로 보관하며 공급자 오류 본문은 보관하지 않는다. 공급자 정상 종료를 애플리케이션 일기 완성으로 간주하지 않는다.
최대 입력은 반복 문장 중심이다. 현재 설정의 단일 호출 처리 가능성은 확인했으나, 각 사례 2회 결과를 성공률 추정이나 반복 안정성 보장으로 사용하지 않는다. 입력 초과가 확정된 사례는 없으며 요약·분할이나 스키마 변경의 근거는 없다. 재발 시 실패 단계 진단을 기준으로 분석하며, 다양한 비반복 대화·최대 AI 문맥·동시 최대 입력 메모리는 미검증이다.

일기 워커를 901초에 중단하고 962초에 재기동을 요청했다. 982초 표본에서 준비 완료를 확인했고 1분 최초 정리 대기 후 1,042초 표본에서 적체가 새 유입 한 묶음 수준으로 회복됐다.
중단·재기동 인근 900~1,050초의 30초 구간별 응답 대기 p95는 68.7~80.1ms다. 4분 시험에서 관측된 2.72초 p95와 달리 이 실행의 구간별 지연은 기준 이내다.
DB 대기 표본에는 지속적인 잠금 대기가 없었고 WAL 쓰기·autovacuum 지연 표본이 각각 한 번 있었다. 10초 표본은 그 사이의 짧은 대기를 모두 포착하지 못한다.
역할별 heap 표본 최고는 API 125.1MiB·대화 119.5MiB·일기 117.2MiB, DB 풀 대기 표본 최고는 API 1·워커 0이며 로그·telemetry 드롭은 0이다.

30일 경과는 과거 시각을 넣어 압축 재현했고 실제 30일·수개월 누적 데이터나 백업 용량을 시험하지 않았다.

따라서 이 30분 범위의 유입·정리 균형은 확인됐지만, 반복 실행 안정성과 콜드 스타트·재기동의 지연 보장까지 승인한 결과는 아니다.

## 해석 범위

시험 poll은 대화 50ms·일기 100ms이며 운영 기본 1초와 다르다.
단기 P1의 완료 작업 정리는 매초 수동 호출한다. 별도의 30분 정리 시험만 운영 10초 주기를 검증했다.
실제 공급자의 다양한 입력 품질·RPM/TPM·서비스 전체 비용, 최대 입력 동시 메모리,
30분·25 RPS·지정 만료 작업 유입량을 넘는 지속 처리와 장기 누적·백업 용량은 미검증이다.
250 RPS는 시험 조건의 지속 요청률이며 순간 동시 접속 수나 실제 운영 최대 용량이 아니다.

로컬 실행 자료는 apps/backend/bootstrap/build/capacity 아래에 생성된다.
자료는 빌드 산출물이며 저장소 문서의 필수 의존 파일이 아니다.
시험 해석의 개발 사례는 [별도 문서](engineering/capacity-validation.md)에 있다.
